# RBH Build 43 — Corrective-Action Email Deep Links

Date: October 6, 2026

## Purpose

Make corrective-action workflow emails open the exact corrective-action item that caused the email instead of opening the entire incident record.

## User-facing behavior

Action-specific notifications now deep-link to the focused corrective-action workspace:

- Corrective action assigned → opens that exact action in its focused work page.
- Changes requested → opens that exact returned action.
- Verification requested / Ready for review → opens that exact submitted action in the focused review page.
- Verification Owner assignment → opens that exact action.

The focused page determines the controls from the live action status and the signed-in user's permissions. The link itself does not grant access.

Report-level notifications remain report-level:

- Investigator assignment → opens the incident record.
- New-report notification behavior is unchanged.

## Technical changes

### dashboard.html

The dashboard now recognizes an `action=<corrective-action-uuid>` query parameter in addition to the existing `report=<report-uuid>` parameter.

When `action` is present:

1. The app waits until authenticated report/action data is loaded.
2. It looks up the exact visible `report_corrective_actions` row.
3. It confirms the related report is available to the current user.
4. It opens the existing focused corrective-action workspace.
5. It clears the URL parameters from browser history after routing.

If the action is unavailable under the user's current permissions, the app does not fall back to opening the broader incident record. It shows an access/unavailable message instead.

### send-action-assignment-email Edge Function

The function now treats `correctiveActionId` as authoritative whenever it is supplied by the dashboard.

For action-specific notifications, the child `report_corrective_actions` row now supplies:

- Action number
- Action description
- Owner
- Due date
- Priority
- Current action status
- Completion note / submitted by
- Verification owner
- Verification note / requested changes

The function validates that the child action:

- belongs to the requested report,
- belongs to the same organization,
- is in the report's current workflow generation,
- is in the report's current reopen cycle,
- has been activated, and
- is not retired.

The email URL is built with both the report and action identifiers, for example conceptually:

`dashboard.html?report=<report-id>&action=<corrective-action-id>`

The dashboard uses the action identifier for the focused route. Authentication and existing Supabase RLS/role rules remain the access-control boundary.

## Backward compatibility

If no `correctiveActionId` is supplied, the function retains the legacy report-level corrective-action behavior. This protects older callers while the application is fully on the multi-action model.

## Deployment

No SQL migration is required.

Two runtime pieces must be updated:

1. Upload the new `dashboard.html` to the RBH GitHub/site deployment.
2. Redeploy the Supabase Edge Function `send-action-assignment-email` using the updated `supabase/functions/send-action-assignment-email/index.ts`.

Updating GitHub alone will not change URLs in emails already generated by the deployed Edge Function.

## Recommended validation

Use a fresh corrective action because notification deduplication intentionally prevents duplicate emails for the same unchanged event.

1. Assign Action #1 to User A and Action #2 to User B.
2. Confirm each assignment email names the correct action and opens only that action's focused workspace.
3. Submit Action #1 for review.
4. Confirm the reviewer email opens Action #1 directly with review controls available to an authorized reviewer.
5. Request changes on Action #1 and confirm the return email opens Action #1 directly.
6. Confirm opening the URL while signed out preserves the route through sign-in.
7. Confirm a user without access cannot gain access merely by knowing/changing an action UUID.
